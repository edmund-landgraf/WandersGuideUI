# Encounter revision guard (#66) — staging only
A database trigger increments the existing encounter_revision for every row update and rejects stale full-row snapshots, including stock create-encounter saves and stale dice writes. The existing narrow MCP writes retain their old-revision UPDATE predicate. The trigger accepts current or current+1 (the latter is the existing narrow CAS contract); this is protection for cooperating writers, not a new authorization mechanism. A writer that intentionally guesses a future revision must not be trusted as an authorization signal. Existing RLS and authorization are unchanged.
 
Before production: verify the real stock create-encounter upsert preserves the revision field, standalone saves and two browsers, overlapping local edits, player action logs, dice, imports, narrow MCP writes, and the archive RPC. Old clients omitting the revision on a whole-metadata write will fail closed once a revision exists. A rejected save must surface an error, reload from the server, and not automatically replay stale snapshots. Verify stock error handling and coordinate API changes if it strips revision. Do not apply this migration to production until that matrix passes.

## Revision-checked save API
Existing Phase 1 encounter saves, standalone renames and MCP encounter metadata/move tools now use `wgui-ext-save-encounter`. It accepts `{encounter_id, encounter_revision, patch}`, checks verified caller and encounter/campaign ownership inside a service-only locked RPC, permits only encounter fields, and returns the committed row with its new revision. The stock create route remains for inserts. Full roster snapshots are still supported but rejected if stale; narrow rename and move preserve unrelated data. Dice writes use an explicit CAS predicate, and the Phase 1 browser sends its observed revision. Legacy dice callers without a revision use a CAS against the server read. Failed saves show an error and reload authoritative data; optimistic log overlays are removed so stale local logs cannot mask a refresh. Overlapping full snapshots are not automatically rebased; a rejected edit must be reapplied manually. The DB guard remains for legacy clients/importers; the upstream stock handler and Phase 0 clients still need live verification. Deploy the SQL after the archive migration, restart edge functions, then deploy the browser/MCP together. No fallback to the old update path. Keep staging-only until live two-browser/AMBA verification passes.

## Cross-RPC concurrency rehearsal
The Encounter revision guard workflow runs `supabase/tests/wgui-encounter-revision-guard-rpc-rehearsal.py` after both migrations and the sequential SQL contracts. A disposable PostgreSQL 16 database runs the actual service-role RPCs in separate sessions; the test verifies lock contention via `pg_blocking_pids` before releasing the first transaction. Both archive-first and save-first orders, identical deliveries, two competing browser saves, reload/reapply, exact SQLSTATEs, revision increments, canonical receipts and metadata mirrors, roster/initiative/dice preservation, and unauthorized direct calls are covered. The script refuses to run without the explicit disposable DB marker. This is database-level verification, not an HTTP/Foundry/two-browser staging test. Keep the staging rollout gate until the real integration matrix passes.
